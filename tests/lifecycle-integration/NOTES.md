# Lifecycle integration draft

This draft is not safe to deploy. Its current tests do not prove the upgrade or downgrade boundary.

- An older installer can overwrite `servus.env` and restore a Compose configuration without the lifecycle mount or entrypoint. Existing installers do not consult the lifecycle state. A trusted host supervisor or another independently enforced guard must prevent routine older-installer reruns from bypassing maintenance. The supervisor must coordinate its installer lock without blocking its own authorized updates.
- The preflight parses `docker compose config --format json` and compares the gate copied from the unstarted image with the release file. Independent review must confirm these checks and their trust boundary, including release source and image authenticity.
- The image environment is inspected before container creation and combined with Compose environment for validation; dangerous inherited loader and Node options are rejected without running the image. A matching revision label or matching wrapper does not authenticate an image. Signature and source-attestation verification must be an independent mandatory gate before deployment.
- A reviewer reproduced this boundary with an image whose `/usr/bin/flock` was replaced: the current checks accepted it because they verify the tool exists and is executable, not its provenance or behavior. Before any image is started, an independent verifier must authenticate the exact registry digest against the intended repository, commit, release ref, authorized workflow and trusted runner. The verified digest must be the one pulled and started, and the verifier must run under a trusted root supervisor with process isolation and fail-closed recovery. Revision labels, wrapper byte equality, and tool presence do not satisfy this requirement. Root/cgroup verifier integration is not ready, so this draft must not be deployed.
- The preflight requires the exact configured environment and mount targets, rejects critical-path data mounts, and does not print the values. It trusts the installed image and the environment of the privileged installer itself; it does not sanitize the interpreter or dynamic loader before installer startup.
- Installer Docker and Compose commands use a cleared environment, an absolute Docker binary, an isolated empty Docker configuration, the default context and the local Unix socket. Canonical Compose validation rejects unknown service fields and verifies the management bind address and port, network, dependencies, health checks and group. Linux fixtures with the actual Docker Compose plugin exercise conflicting inherited variables and confirm that proxy settings in `/root/.docker/config.json` are not injected into created containers. The isolated client configuration cannot use credentials or proxy settings stored in the user's Docker configuration; an explicit trusted mechanism would be needed for private registries or controlled proxies. The older installer bypass remains unresolved.
- The current draft stores a resolved Compose snapshot containing the origin, port and proxy secret. The existing origin migration changes `servus.env` but does not regenerate this snapshot, so enabling the draft would break origin updates. A shared, authenticated regeneration procedure under `install.lock`, including atomic recovery and tests for origin and proxy changes, is required before deployment. Treat the snapshot as secret material and retain it with mode 0600 in a root-only directory.
- The installer unit fixtures mock lifecycle preparation and image/Compose preflight. Isolated Docker tests exercise the real checks and Compose separately, but do not exercise a full installer upgrade against a real daemon or any old-installer downgrade.
- Gate creation writes a directory and marker separately. A crash between those operations leaves an incomplete gate and requires manual recovery. The draft must not create or restore `normal` automatically in that state.
- A lifecycle inode must remain stable through the life of the installation. Root is trusted and must never replace or unlink the lock. A separate host supervisor must enforce and verify that contract, durable maintenance state, and recovery ordering.
- Supervisor control uses a root-owned socket directory and three distinct root-owned, group-readable per-role token files mounted individually read-only. Provisioning never rotates existing tokens; a partial creation is fail-closed and needs recovery. Before changing the running Compose configuration, the installer requires a live socket with the expected ownership and mode. Its root probe only proves a stream listener exists, not its identity or successful component authentication; the supervisor must tolerate the probe being closed without a handshake.
- The control daemon, its independently provisioned runtime policy, startup/reboot ordering, and installer coordination are not integrated here. Components require the supervisor socket to exist before opening their data stores. This draft cannot provide a working first install or upgrade unless a compatible daemon is started after credential provisioning and before Compose, without holding the installer lock needed by the installation. No fallback to an unguarded installation is permitted.
- The isolated Compose test uses synthetic Node processes and a test-only Unix listener. It proves role-specific read-only mounts, ownership and connection, but does not exercise authenticated role handshakes, real component drain, runtime-policy generation, or production daemon recovery. Installer upgrade testing mocks image and Compose verification to isolate the missing-socket path; it is not a complete real upgrade test.
- The coordinator must hold the shared installer lock while changing lifecycle state. The installer currently releases its shared lifecycle lock before writing the environment and starting Compose; without the installer lock, those steps can race maintenance.
- The new lifecycle mount and entrypoints change the expected Compose configuration. Update and retest the preflight verifier before connecting it to this release.
- A SIGKILL between `docker create` and recording the inspection container ID can leave an unstarted orphan. Normal failures and catchable exit paths remove only the recorded ID. A future supervisor needs a safely attributable probe identity and recovery policy; it must not remove another container after a name conflict.
- Lifecycle locking only covers cooperating processes. It does not exclude unrelated writers, Docker operators, application volumes, or unresolved agent operations. No snapshot or automatic update can be authorized solely by this gate.
